# Ревью кода перед итерацией 8

Дата: 2026-10-04. Проверены Telegram ingestion и управление, LLM-распознавание, корреляция, trade planner и approvals, публичная проверка MEXC, paper executor, SQLite-миграции, Web UI, тесты, операторские сценарии и документация.

## Итог

Критических дефектов после исправлений не осталось. Текущая версия пригодна для продолжения paper-разработки в итерации 8. Live execution по-прежнему отсутствует и заблокирован как в UI, так и в обработчике управляющих команд.

## Исправлено во время ревью

- Web UI разрешает подтверждать `close_partial`, `close_full`, `set_stop` и `set_take_profit` без отдельной `market_check`. Публичная MEXC-проверка обязательна только для `open` и `add`. Это устраняет тот же класс ошибки, который ранее скрывал кнопку подтверждения в Telegram.
- Обновление mark price открытой paper-позиции ограничено интервалом около двух секунд. Раньше цикл обновлял одну позицию несколько раз в секунду, без пользы увеличивая `version` и SQLite WAL.
- Ошибка публичной котировки переводит paper worker на обычный backoff, а не в частый цикл повторов.
- Paper executor больше не считает отсутствующую taker-комиссию или maintenance margin нулевыми. Неполные спецификации MEXC закрываются безопасно, чтобы не завышать виртуальный результат и не искажать ликвидацию.
- Ошибка исполнения ожидающего trigger-limit теперь создаёт отдельное уведомление владельцу наряду со статусами `failed` у заявки и плана.
- Карточка распознавания больше не утверждает, что позиций и ордеров нет. Текст нейтрален для recognition и paper, а фактическое состояние отдано карточке плана.
- Документация paper MVP отделена от целевых требований: funding, частичные fills одного ордера и отдельная модель проскальзывания пока не заявлены как реализованные.

## Автоматическая проверка

Команды выполнялись в проектной `.venv`:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m compileall -q bootstrap.py recognition-status.py trader tests
.\.venv\Scripts\python.exe -m pip check
```

Полный набор содержит 95 тестов. Он проверяет валидацию и один контролируемый repair LLM-ответа, корреляцию reply-chain и фактических позиций, планирование и резервы банка, версионированные approvals, MEXC-спецификации, market/trigger-limit paper execution, частичные и полные закрытия, SL/TP, комиссии/PnL, отказоустойчивость, миграции, CSRF/Origin, HTMX polling и управляющие команды. Сетевые smoke-тесты в обычный набор не входят.

Стандартный `trace` показал 73,0% line coverage прикладных Python-модулей (2501 из 3424 обнаруженных исполняемых строк). Для ключевых модулей: correlation 93,6%, web repository 90,2%, paper 86,3%, agent 85,8%, planner 84,5%, store 85,0%. У долгоживущего `service.py` показатель 40,9%: локальные тесты покрывают отдельные шаги ingestion, worker, approvals и control, но не держат реальные Telegram/Bot API соединения. Значение служит ориентиром и не является branch coverage.

AST-проверка 32 Python-файлов не нашла неиспользуемых импортов и недостижимых приватных определений верхнего уровня. `compileall` завершился без ошибок, `pip check` не обнаружил конфликтов зависимостей.

## Исполняемые файлы

Неиспользуемых исходных исполняемых файлов не найдено:

- `setup-local.cmd` выполняет первичную проверку, авторизацию reader и привязку владельца;
- `start-recognition.cmd` и `start-recognition-background.cmd` запускают reader;
- `start-ui.cmd` и `start-all.cmd` запускают Web UI отдельно или вместе с reader;
- `status-recognition.cmd` и `watch-recognition-log.cmd` показывают состояние и журнал;
- `stop-recognition.cmd`, `stop-ui.cmd` и `stop-all.cmd` останавливают процессы;
- `recognition-status.py` используется сценарием статуса;
- `tests/smoke_live.py`, `tests/smoke_paper_public.py` и `tests/replay_failed.py` являются документированными ручными диагностическими точками входа.

Оба PowerShell-сценария разобраны через `ScriptBlock.Create`; все ссылки из `.cmd` и `.ps1` ведут на существующие файлы. `__pycache__` и `*.pyc` — генерируемый кеш Python, исключённый `.gitignore`, а не часть исходного кода.

## Эксплуатационная проверка

Reader и Web UI перезапущены из обновлённого кода. Reader подтвердил авторизацию пользовательского Telegram-аккаунта, доступ к включённому каналу, owner chat и управляющему боту, затем записал `READY`. Heartbeat видит один включённый и подключённый канал, пауза выключена, очередь управляющих команд пуста, stderr reader пуст.

`/healthz` вернул HTTP 200 и schema version 8. Страницы `/`, `/channels`, `/posts`, `/trades`, `/stats`, `/control` и HTMX partial `/partials/trades` вернули HTTP 200; stderr UI пуст. Режимы после restart сохранились как `paper/manual`. Последний план полного закрытия имеет статус `executed`, paper-позиция AVAUSDT закрыта с нулевым остатком. Во время ревью планы не подтверждались и торговые действия не инициировались.

## Границы проверки

Автотесты не публикуют сообщения в Telegram, не вызывают платную LLM и не используют private MEXC endpoints. Интеграционные ветки долгоживущего Telegram reader имеют более низкое line coverage, чем детерминированные модули; их реальная готовность проверяется heartbeat, журналами и безопасным restart.

До live-режима всё ещё нужны private MEXC adapter, идемпотентное восстановление после неизвестного результата API, сверка позиций и ордеров с биржей, подтверждённая isolated margin на каждом запросе, аварийные запреты и отдельный набор sandbox/минимальных live-проверок. Эти возможности не скрыты за текущим переключателем: значение `live` отвергается сервером.
