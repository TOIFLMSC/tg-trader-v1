# Ревью кода перед итерацией 4

Дата: 2026-10-03. Область проверки: распознавание Telegram-сообщений, локальное хранилище, Web UI трёх первых итераций, управляющие команды и локальные сценарии запуска. Торгового исполнения в этой версии нет.

## Итог

Критических дефектов в проверенной версии не осталось. Схема базы мигрируется идемпотентно, события и команды сохраняются до обработки, ошибки распознавания закрываются безопасно, а Web UI не может включить ещё не реализованные режимы paper/live. Версия пригодна как основа итерации 4.

## Исправлено во время ревью

- Удалены устаревшие параметры `TRADING_MODE` и `APPROVAL_MODE` из примера окружения и проверки запуска. Фактические режимы хранятся в SQLite и меняются через очередь команд.
- История и кандидаты сделок теперь берут только последнюю завершённую версию каждого поста. Правка Telegram-сообщения больше не оставляет конкурирующий старый кандидат.
- Повторное сохранение того же значения настройки не создаёт новую версию и лишнюю запись аудита.
- Счётчики пустых каналов возвращают нули; число ожидающих команд считается по всей очереди, а не по последней странице.
- Убран второй путь постановки управляющей команды: Web UI использует реализацию `Store.queue_control`.
- Проверка медиа ограничивает путь каталогом `data`, размер — 8 MB, тип — расширением из разрешённого списка, а сохранённые файлы дополнительно сверяются по SHA-256. MIME из Telegram или базы не считается доверенным.
- Все изменяющие Web UI запросы требуют CSRF-токен и точное совпадение Origin. Ответы получили CSP, запрет MIME sniffing и встраивания во frame.
- Один шаг обработки события и одна управляющая команда выделены из бесконечных циклов в тестируемые методы. Исключения не сохраняют секретный текст; событие получает статус ошибки.
- Повторная проверка недоступного Telegram-канала ограничена интервалом 60 секунд.
- Фоновый launcher проверяет PID, ждёт PID самого reader и строку готовности. `start-all.cmd` больше не запускает UI, если reader не подтвердил готовность.
- Удалены неиспользуемые импорты и поле состояния; актуализированы README, мастер настройки и описание UI.
- Версии runtime-зависимостей зафиксированы в `requirements.txt` на проверенных версиях.

## Автоматическая проверка

Команды выполнены в проектной `.venv`:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m compileall -q bootstrap.py recognition-status.py trader tests
.\.venv\Scripts\python.exe -m pip check
```

Результат: 49 тестов, 0 ошибок; все Python-файлы компилируются; конфликтов установленных зависимостей нет. PowerShell-файлы разобраны через `ScriptBlock.Create` без синтаксических ошибок. Отдельный AST-скан не обнаружил неиспользуемых импортов; декорированные Pydantic-валидаторы и обработчики FastAPI считаются точками входа фреймворков.

При измерении стандартным модулем `trace` исполнено 957 из 1876 обнаруженных исполняемых строк (51,0%). Для основных модулей с чистой бизнес-логикой результат выше: correlation 81,6%, migrations 81,2%, repository 75,6%, store 72,5%, agent 70,8%, Web app 58,7%. Общий показатель снижают интерактивный bootstrap, скрипт статуса и долгоживущие сетевые ветки service. Процент служит ориентиром: `trace` не заменяет branch coverage и иначе учитывает код, созданный декораторами.

Тесты проверяют в том числе миграцию старой базы, дедупликацию и правки постов, бюджет LLM, безопасный повтор разбора, корреляцию сделок, валидацию чисел, паузу, очередь и аудит команд, динамический список каналов, отказоустойчивость worker, CSRF/Origin, идемпотентность форм, фильтры UI и безопасную выдачу изображений.

## Исполняемые файлы

Неиспользуемых операторских сценариев не найдено:

- `setup-local.cmd` запускает первичную проверку, Telegram-авторизацию и привязку владельца;
- `start-recognition.cmd` и `start-recognition-background.cmd` запускают reader в видимом или фоновом режиме;
- `start-ui.cmd` и `start-all.cmd` запускают панель отдельно или вместе с reader;
- `status-recognition.cmd` и `watch-recognition-log.cmd` показывают состояние и журнал;
- `stop-recognition.cmd`, `stop-ui.cmd` и `stop-all.cmd` останавливают соответствующие процессы;
- `tests/smoke_live.py` — явная платная проверка реальной модели без Telegram и сделок;
- `tests/replay_failed.py` — явный локальный переразбор одного события без уведомления и изменения исходного события.

Файлы `*.pyc` и каталоги `__pycache__` являются генерируемым кешем Python, исключены `.gitignore` и не относятся к исходному коду.

## Эксплуатационная проверка

После ревью reader и UI остановлены штатными командами и запущены заново из обновлённого кода. Проверка `trader.service --check` подтвердила Telegram-сессию, доступ к начальному каналу, личному чату владельца и Bot API. Фоновый launcher дождался строки `READY` и фактического PID сервиса.

`/healthz` вернул HTTP 200, схему 4, один канал и 11 сохранённых событий. Страницы `/`, `/channels`, `/posts`, `/trades`, `/stats` и `/control` вернули HTTP 200. Проверены CSP, `nosniff`, запрет frame, referrer policy и permissions policy. Команды pause и resume прошли через настоящий HTTP endpoint и общую очередь, были применены reader и оставили очередь пустой; итоговое состояние — распознавание включено. Журналы reader и UI не содержат ошибок.

## Границы проверки

Автотесты не отправляют реальные сигналы в Telegram и запросы OpenAI, чтобы не менять внешнее состояние и не расходовать бюджет. Read-only подключение к Telegram и Bot API проверено при холодном старте. Полный платный smoke LLM остаётся ручной командой.

Перед реальной торговлей потребуются отдельные контрактные тесты MEXC, моделирование частичных исполнений и комиссий, аварийное восстановление после неизвестного результата API, сверка локальной позиции с биржей и независимые запреты live-режима. Эти задачи относятся к следующим итерациям и не скрыты за текущими переключателями UI.
